有限的 RAM，無限的程式：OS 如何管理記憶體？

💡 白話比喻：硬碟是大書櫃（容量大但拿取慢），RAM 是書桌桌面（空間有限但隨手能翻），而 CPU 就是正在讀書的你——書必須放上書桌才能閱讀與修改！

1. 隔離與保護 (Protection)

CPU 僅能直接存取 Registers 與 Main Memory（Cache 居間緩衝）。多工時須防止程式越界讀寫其他行程或 OS 核心。

2. 空間效率 (Utilization)

避免「外部斷裂（External Fragmentation）」與「內部斷裂（Internal Fragmentation）」浪費寶貴實體 RAM。

3. 位址虛擬化 (Virtualization)

將程式邏輯位址與實體 RAM 解耦，透過 Demand Paging 與 TLB 兼顧大空間與高速存取。

Ch 06 · 硬體保護與位址綁定 02 / 16

畫出安全圍欄：Base/Limit Registers、MMU 與位址綁定

💡 白話比喻：給每本書記住「起點門牌 (Base)」與「可用寬度 (Limit)」，再用門房翻譯官（MMU）把程式以為的「我的第 10 頁」翻譯成書桌真實座標。

專業機制 1：硬體位址保護

User Mode 下每次記憶體存取，CPU 硬體皆即時驗證範圍，若越界立刻觸發 Trap（Addressing Error）交由 OS 終止行程：

base≤address<base+limit

專業機制 2：Logical vs. Physical & MMU

CPU 產生 Logical（Virtual）Address；執行期間由 MMU（Memory-Management Unit） 將其加上 Relocation Register，動態映射為記憶體單元看到的 Physical Address。

三種 Address Binding（位址綁定）時機

  • Compile Time：編譯時已知實體位置，直接產生 Absolute Code（若位置變動須重新編譯）。
  • Load Time：編譯時未知位置，須產生 Relocatable Code，於載入記憶體時綁定；兩者中 Logical = Physical Address。
  • Execution Time：綁定延後至執行期（現代 OS 主流），允許行程在執行中搬移位置，需 MMU 硬體支援。

Ch 06 · 連續配置與斷裂 03 / 16

連續配置（Contiguous Allocation）與 50-Percent Rule

💡 白話比喻：早期規定每本書必須「一整本連在一起」放桌上；舊書收走後留下的零碎空洞（Hole）常塞不進新書，就像瑞士起司一樣滿是孔洞。
First-Fit 統計分析：50-Percent Rule（外部斷裂空間浪費）
Unusable Memory Ratio= 0.5NN+0.5N =13

專業解讀：在 Dynamic Storage-Allocation（First-Fit 找首個夠大空洞、Best-Fit 找最小夠大洞、Worst-Fit 最差）下，每配置 N 塊就會產生 0.5N 個無法利用的碎洞，約 1/3 記憶體浪費！

⚠️ External vs. Internal Fragmentation

External：總可用空間足夠但不連續，須靠 Dynamic Relocation + Compaction（壓實搬移）合併；Internal：配置區塊略大於實際需求（固定分區內未用空間）。

Swapping（換頁搬移）的時間代價

將 100 MB 行程以 50 MB/s 磁碟 Swap Out（2,000 ms）再 Swap In（2,000 ms），單次 Context Switch 的 Swapping 開銷高達 4,000 ms（4 秒），極度緩慢。

Ch 06 · 分段架構與教材演進 04 / 16

Segmentation（分段）與跨版本演進（9th vs. 10th Ed.）

💡 白話比喻：把書拆成「正文、表格、附錄」分開找位子放，雖然比整本靈活，但因為每段長短依然不同，用久了桌上還是會留下碎洞！

專業架構：Segment Table 與保護位元

  • 邏輯位址為雙元組 <segment-number s, offset d>，由 STBR（表起點）與 STLR（段數量）檢查合法性（s<STLR 且 d<limit）。
  • 每筆記錄 (base, limit) 與 Valid Bit、Read/Write/Execute 權限，支援以邏輯段為單位的程式碼共享。
  • 🔑 致命限制：段長不一使配置仍屬動態配置問題，External Fragmentation 依然存在。

⚠️ 教材重大演進：9th (2013) → 10th Ed. (2018)

  • 9th Ed.（[[Silberschatz2013-OS-Ch06-Memory]]）：獨立講授 Segmentation 與整支 Process Swapping。
  • 10th Ed.（[[Silberschatz2018-OS-10thEd]]）：因現代 64-bit 系統全面採平坦定址，正式移除 Segmentation 專節，並將 Swapping 改為現代 OS 實務的 Page Swapping，補充 ARMv8 64-bit 架構。

Ch 06 · Paging 硬體翻譯與計算 05 / 16

Paging（分頁）：用活頁紙機制徹底消滅外部斷裂

💡 白話比喻：把書拆成等大的「活頁紙（Pages）」，書桌畫成同大的方格（Frames），靠目錄清單（Page Table）記錄「第幾頁放第幾格」，就能打散存放！

專業機制：位址切分與硬體翻譯

  • 實體記憶體切為固定大小 Frames，邏輯記憶體切為同大 Pages（2 的冪次，常見 512 B 至 16 MB）。
  • 若邏輯位址空間 2m、Page Size 2n：高 m−n bits 為 Page Number (p)，低 n bits 為 Page Offset (d)。
  • MMU 以 p 查詢由 PTBR 指向的 Page Table 取得 Frame Number f，再拼上 d 成為實體位址。

🔑 斷裂精算與 Shared Pages

  • External Fragmentation = 0：任何 Free Frame 皆可配給任何行程（OS 以 Free-Frame List 追蹤）。
  • Internal Fragmentation 算例：若 Page Size = 2,048 B、Process = 72,766 B = 35 pages + 1,086 B，最後一頁浪費 2,048−1,086=962 B（平均浪費 12 Page）。
  • Shared Pages：唯讀可重入程式碼（Reentrant Code，如編譯器）可讓多個行程 Page Table 指向同一實體 Frame。

Ch 06 · TLB 與有效存取時間 06 / 16

TLB 硬體快取與 Effective Access Time (EAT) 推導

💡 白話比喻：在書桌角貼一張「速查便利貼（TLB）」，記住最近常翻的那幾頁在第幾格；99% 瞄一眼便利貼就找到，不必每次翻厚重的目錄清單！

專業架構：Associative Memory & ASIDs

TLB（Translation Look-aside Buffer） 是 64–1,024 entries 的平行搜尋關聯式快取。若 TLB 支援儲存 ASID（Address-Space Identifier），便能在 Context Switch 時保護位址空間而無須清空（Flush）整個 TLB。

TLB 有效存取時間（RAM 存取 m=100 ns，TLB 搜尋 ϵ=20 ns，命中率 α）
EAT= (m+ϵ)α+ (2m+ϵ)(1−α)

數值對比：命中（機率 α）只讀 1 次 RAM；TLB Miss（機率 1−α）須讀 Page Table＋資料共 2 次 RAM。當 α=80% 時 EAT=140 ns；當 α=99% 時降至 121 ns！

Ch 06 · 64-bit Page Table 結構 07 / 16

大型 Page Table 瘦身術：Hierarchical、Hashed 與 Inverted

💡 白話比喻：目錄厚到書桌放不下時，可以「先印總目錄再分章節目錄」、「用頁碼直接算雜湊櫃號」或「全書桌只寫一張格子分配表」。

為什麼單層 Page Table 會爆炸？ 32-bit 位址搭 4 KB (212) 頁需要 220≈100 萬筆（約 4 MB 連續空間）；而 64-bit 位址空間更達 252 筆，完全無法一次塞進實體 RAM。

Page Table 結構專業運作機制空間優勢查詢代價與限制
Hierarchical Paging
（多層分頁表）		將 Page Table 本身再分頁（如 2-Level p1+p2+d 或 3-Level 32+10+10+12 bits），採 Forward-mapped 樹狀索引未使用的稀疏位址區段無須配置內層表64-bit 若分 4 層，TLB Miss 時須 4 次記憶體存取
Hashed Page Tables
（雜湊分頁表）		常見於 >32-bit 空間：將 Virtual Page Number 經 Hash Function 對應至 Bucket，沿 Linked-list 比對 (VPN, Frame, Next)表大小只與實際使用的頁面數量成正比；Clustered 變體每筆管 16 頁發生 Hash Collision 時須走訪串鏈
Inverted Page Table
（反向分頁表）		全系統僅維護一張表，每個實體 Frame 對應一筆 <pid, p>，以實體位置反查擁有者極度節省記憶體（不隨行程數量膨脹）須靠 Hash + TLB 加速搜尋；跨行程共享記憶體映射較困難

Ch 07 · Virtual Memory 誕生 08 / 16

Virtual Memory（虛擬記憶體）：邏輯與實體徹底解耦

💡 白話比喻：看 1,000 頁百科全書時，同時只會翻開其中 3 頁；另外 997 頁（例如「冷門錯誤處理說明書」）根本可以先留在書櫃（硬碟）！

1. 突破實體 RAM 上限

允許執行「部分載入（Partially-loaded）」的程式，Logical Address Space 可遠大於 Physical Memory。

2. 提升並行度與效率

每支行程只佔少數 Frames，RAM 可同時容納更多行程，減少 Swapping 與無謂 I/O，加速 fork() 建立。

3. Sparse Address Space

Code/Data 在底、Heap 向上長、Stack 向下長，中間保留廣大 Hole 供動態成長與共享函式庫映射。

實作途徑與核心概念

Virtual Memory 可透過 Demand Paging（主流）或 Demand Segmentation 實作；唯有實際被執行或存取到的程式碼區段才會真正佔用實體頁框。

Ch 07 · Demand Paging 09 / 16

Demand Paging（需求分頁）與 Page Fault 處理 6 步驟

💡 白話比喻：像餐廳「點菜才上菜（Lazy Swapper）」！目錄每頁旁畫一個勾：v 代表已在書桌上，i 代表還在書櫃——摸到 i 就請 OS 去書櫃拿！

專業機制：Pager & Valid-Invalid Bit

  • Lazy Swapper (Pager)：以 Page 為單位（非整支行程），沒用到絕不搬入記憶體；Extreme Case 為 Pure Demand Paging（從 0 頁開始執行）。
  • Valid-Invalid Bit：Page Table 每列附加狀態位元：v（Memory Resident，已在 RAM）vs. i（Not-in-memory 或非法存取）。
  • 硬體需求：Page Table（含 v/i bit）、Secondary Memory（Swap Space）與 Instruction Restart。

Page Fault 發生時的 6 步 OS 救援

  • 1. 存取標記為 i 的頁面 → 觸發 Page Fault Trap 給 OS。
  • 2. OS 查內部表確認：非法位址則 Abort；合法則僅是不在 RAM。
  • 3. 從 Free-Frame List 取得一個空 Frame。
  • 4. 排程 Disk Read 將該頁從 Backing Store 讀入空 Frame。
  • 5. 更新 Page Table 框號並將驗證位元改為 v。
  • 6. Restart 被中斷的指令（如 load M），程式無縫繼續！

Ch 07 · EAT 與局部性救星 10 / 16

Page Fault 的效能雪崩：千分之一錯失＝慢 40 倍！

💡 白話比喻：書桌拿資料只要 200 奈秒，跑去書櫃拿要 8 毫秒（慢 40,000 倍！就像書桌拿筆 1 秒 vs. 坐飛機出國拿筆 11 小時）。
Demand Paging 有效存取時間（RAM 200 ns，Page Fault 服務 8 ms=8,000,000 ns，缺頁率 0≤p≤1）
EAT=(1−p)×200+p×8,000,000=200+7,999,800p
慢 40 倍！

若每 1,000 次存取發生 1 次 Page Fault（p=0.001），EAT=8,199.8 ns≈8.2 μs。若要效能衰退 < 10%（<220 ns），須 p<0.0000025（40 萬次少於 1 次）。

🔑 為什麼實務上還能跑得飛快？

仰賴 Locality of Reference（參考局部性）：程式在時間與空間上高度集中存取相鄰頁面，使實際 p 極接近 0。

Ch 07 · Copy-on-Write 11 / 16

Copy-on-Write (COW)：先共用，真的要改再影印！

💡 白話比喻：爸爸開分身（fork()）時，先讓父子合看書桌上同一疊活頁紙；只有當某一方真的拿筆「塗改」某一頁時，才立刻影印那一頁給他！

專業流程 1：fork() 當下共享唯讀頁

傳統 fork() 複製整份記憶體，但子行程常緊接呼叫 exec() 覆寫空間而浪費。COW 讓父子行程的 Page Table 指向同一組實體 Frames（如 Page A, B, C）並標為 Copy-on-Write，瞬間完成行程建立。

專業流程 2：寫入觸發複製與 vfork()

當 Process 1 嘗試修改 Page C 時，硬體觸發保護例外，OS 從 Free-Frame Pool 配置新框並複製出「Copy of Page C」供其修改；vfork() 則讓父行程暫停、子行程共用位址空間直到 exec()。

🔒 安全與記憶體衛生：Zero-Fill-on-Demand

Free Frames 在配置給新行程使用前會先清零（Zero-out），防止新程式讀取到先前已終止行程留下的敏感記憶體殘留。

Ch 07 · Page Replacement 12 / 16

Page Replacement：Dirty Bit 與 FIFO / OPT / LRU 演算法比較

💡 白話比喻：書桌滿了要收走一頁前，先看有沒有塗改過（沒改過直接蓋掉！）；再比比看「最早放上桌」、「會算命」和「最久沒翻」誰最省力。

Modify (Dirty) Bit 減半 I/O：替換 Victim Frame 時，若該頁未被修改（Dirty = 0）則無須寫回磁碟、直接覆寫；僅 Dirty = 1 才須兩次頁面傳輸（寫出＋讀入）。以下以字串 7,0,1,2,0,3,0,4,2,3,0,3,2,1,2,0,1,7,0,1（3 Frames）評測：

演算法挑 Victim 規則Page Faults專業特性與優缺點
FIFO（先進先出）最早進入 RAM 的頁面15 次實作簡單（FIFO Queue），但存在 Belady's Anomaly
Optimal (OPT)未來最久不會被用到的頁面9 次理論最佳下界基準，但 OS 無法預知未來，無法實作
LRU（最近最少使用）過去最久未被存取的頁面12 次效果佳且屬 Stack Algorithm（無異常），但 Counter / 雙向鏈表維護成本高

⚠️ 什麼是 Belady's Anomaly（貝萊迪異常）？

在 FIFO 下對特定字串（如 1,2,3,4,1,2,5,1,2,3,4,5），增加實體 Frame 數（3 → 4 格）反而導致 Page Fault 次數上升！OPT 與 LRU 因具包含性質（Stack Algorithms）絕不發生此異常。

Ch 07 · 實務近似置換策略 13 / 16

實務近似演算法：Second-Chance (Clock) 與 Counting

💡 白話比喻：把桌上的頁排成圓圈貼「剛看過 1」的貼紙；時鐘指標看到 1 就撕掉改 0 給第二次機會，看到 0 代表很久沒理它，直接收走！

Second-Chance (Clock) 演算法

  • 硬體為每頁提供 1 個 Reference Bit（被存取即設為 1）。
  • 指標掃描環狀佇列：若 Ref = 1，將其清為 0（給第二次機會）並推進指標；若 Ref = 0，立刻選為 Victim 替換。

Enhanced Second-Chance（雙位元）

綜合 (Reference Bit, Modify Bit) 決定 4 級淘汰優先序：
(0,0) 最佳（未用且乾淨）→ (0,1)（未用但須寫回）→ (1,0)（剛用但乾淨）→ (1,1) 最差（剛用且髒）。

Page Buffering 與 Counting 演算法

Page Buffering 預先維護 Free-Frame Pool 與 Modified List（空閒時寫回磁碟以維持乾淨）；Counting 則包含 LFU（踢參考次數最少者）與 MFU（實務極少採用）。

Ch 07 · Frame Allocation & Thrashing 14 / 16

Frame Allocation 與 Thrashing（輾轉）系統危機

💡 白話比喻：一次在書桌擺太多本書、每本只分 1 格，結果「剛把第 5 頁放回書櫃、下一秒又要拿第 5 頁」，全部時間都在跑書櫃、完全沒辦法讀書！

Frame Allocation 與 Global / Local 策略

除了均分（Equal），更常依行程大小 Si 按比例分配總可用框數 m（Proportional Allocation，如 m=64,S1=10,S2=127⇒a1≈5,a2≈59）：

ai=Si∑Sj×m

Global Replacement 可從低優先權行程搶框（吞吐高但效能不穩）；Local 僅替換自身框。

⚠️ Thrashing（輾轉）的惡性循環

  • 當分配到的 Frames 少於行程 Locality（目前活躍工作集）所需大小，Page Fault 率急遽飆升。
  • 行程忙著換頁（Swapping in & out）導致 CPU 利用率驟降。
  • OS 排程器誤以為系統負載不足，反而提高 Degree of Multiprogramming（再加開新行程）→ 大家更缺框 → 系統全面卡死！

防治 Thrashing（Working-Set / PFF）與核心配置器

💡 白話比喻：統計每本書最近常翻的幾頁，總和超過桌面格數就先請幾本書下桌休息；OS 核心自己拿空間則用「對半切夥伴」或「專用零件盤」。

防治 Thrashing：Working-Set & PFF

  • Working-Set Model：定義視窗 Δ（如 10,000 次參考）內的不重複頁面數為 WSSi，總需求 D=∑WSSi。若 D>m（實體框總數），OS 必須暫停或換出部分行程。
  • Page-Fault Frequency (PFF)：搭 Local Replacement 設定可接受缺頁率上下界——高於上限加框、低於下限收框，比 Δ 追蹤更直接好實作。

Kernel Memory Allocators（核心專用配置）

  • Buddy System：將實體連續頁按 2k 對半切分（如 256 KB 拆成 128→64→32 KB 滿足 21 KB 請求），釋放時快速與相鄰夥伴（Buddy）合併，缺點仍有內部斷裂。
  • Slab Allocator：為每個核心資料結構建立 Cache（內含物理連續頁構成的 Slabs 與預建物件），完全無內部斷裂且配置極快。

迴圈方向差 128 倍！全章雙軌核心結論

💡 白話實例：讀 128 × 128 表格（每橫列剛好放一頁），「直著跨列跳著讀」跑 16,384 趟書櫃；「順著橫列連續讀」只要 128 趟！

專業實戰：Program Structure & TLB Reach

假設 int data[128][128] 以 Row-major 儲存且每列佔 1 Page：外層掃 j（Column-major）產生 128×128=16,384 次 Page Fault；改為外層掃 i（Row-major）僅需 128 次！另可透過 Multiple Page Sizes 擴大 TLB Reach=TLB Size×Page Size，並以 I/O Interlock 鎖定 DMA 緩衝頁。

🔑 四大核心結論（Key Takeaways）

  • 隔離與綁定：Base/Limit 與 MMU 在 Execution Time 分離邏輯與實體位址。
  • 分頁與 TLB：Paging 徹底消滅外部斷裂；99% 命中率的 TLB 把兩倍查表拉回 121 ns。
  • 虛擬記憶體：Demand Paging + COW + Clock + Working-Set 兼顧大空間與防 Thrashing。
  • 10th Ed. 演進：正式淘汰 Segmentation，轉向 NUMA、Compressed Memory 與雲端虛擬化。
